- 0.4.3 的“检查更新”能发现 0.4.4 并弹出确认，但旧版校验文件跨域请求报 `TypeError: Failed to fetch`，没有完成自升级。不能据此宣称旧版软件内升级成功。
- 随后由本次构建的 0.4.4 原生更新模块发起修复升级：真实下载 GitHub Windows Release 安装包，校验 SHA-256，退出更新模块，静默覆盖安装，自动重新打开已安装程序。没有把手动运行安装器冒充软件内升级；这一步是测试版修复模块辅助升级，非旧版原入口完成的闭环。
- 安装包 SHA-256：`cff4e93acdfce5a7272253fd2fb99a1c1aa1ae930570441a34549a41e4293de9`。
- 安装目录 BUILD-INFO 与卸载注册表版本均为 0.4.4，源提交为 `544ecd2`；重新打开的进程来自安装目录，关于页显示“已是最新版本 V0.4.4”。
- 安装后的实际窗口恢复、最大化、全屏、退出全屏均检查了左边缘，误差小于 1 CSS 像素；保留安装后首页、歌词页、关于页截图。
- 原生启动参数补验：安装标记加 `--installed-first-launch` 显示完整前奏；普通启动即使遗留标记也不显示完整前奏；关闭日常动画直接进入界面。
- 网络测试中代理出口曾返回 GitHub 403，绕开 API 代理后恢复；未向程序保存 GitHub 凭据。

可重跑：`node scripts/check-release-ux.mjs`；Windows 原生模式先将 `RHINE_DESKTOP_EXE` 指向构建的可执行文件，再运行同一脚本。原生模式采用独立测试数据/浏览器目录；运行前关闭其他 RhineMusic 实例。

补记：最终逐项复查发现 0.4.4 的手动“完整启动动画”仅重播音乐前奏，未包含原始白色加载开场。此遗漏在后续 0.4.5 补齐，并增加对 `.rhine-loading` 实际出现及跳过后交接的运行断言。另发现发布标签触发旧工作流重复构建、重新上传了同名资产；本记录中的 SHA-256 是当时实际验证的包。标签源提交未改写，0.4.5 后续已增加防止重复发布覆盖的工作流保护。
